# گردش‌کار Git پروژهٔ Rival_Frontend

## مخزن و نسخهٔ پایدار

- تصمیم مالک در ۲۰۲۶-۱۱-۱۶ جایگزین گردش‌کار قبلی شاخه‌های دائمی فرانت‌اند و بک‌اند است (DEC-059).
- مخزن `https://github.com/mbatvaz/Rival_Frontend` فقط برای توسعهٔ فرانت‌اند است؛ `origin` به همین نشانی با پسوند `.git` متصل می‌شود.
- `master` محل نسخهٔ نهایی پایدار است؛ شاخه‌های دائمی `frontend`، `backend` و شاخه‌های `stable/*` حذف می‌شوند.
- solution خالی بک‌اند حذف می‌شود. تاریخچه بازنویسی نمی‌شود؛ قراردادهای API، منابع طراحی و راهنمای مهاجرت آینده جزو مرجع فرانت‌اند باقی می‌مانند.
- نسخه‌های پایدار با تگ annotated و تغییرناپذیر مشخص می‌شوند. تگ منتشرشده جابه‌جا نمی‌شود.
- تگ `stable/baseline-1` روی `f28ee4f7410d4806134abd551c11e9b46657865b` جایگزین شاخهٔ سابق هم‌نام است؛ این نقطهٔ بازیابی به‌تنهایی گواه قبولی تست یا پذیرش فاز نیست.
- تگ `stable/phase-03` نسخهٔ نهایی پذیرفته‌شده تا فاز ۰۳ را پس از اصلاح ساختار مشخص می‌کند. پذیرش محصول در [پیشرفت](../PROGRESS.md) و DEC-058 ثبت شده است.
- تگ `stable/phase-04` نسخهٔ پذیرفته‌شدهٔ پنل مشتری تحت DEC-086 را مشخص می‌کند. [مدارک تحویل](../docs-work/PHASE_04_CLOSEOUT_FA.md)

## چرخهٔ هر فاز

1. فقط پس از تخصیص صریح مالک، وضعیت تمیز مخزن و همگامی `master` با `origin/master` بررسی شود؛ دریافت با `git fetch origin --prune` و به‌روزرسانی با `git pull --ff-only` انجام شود.
2. فاز تازه در شاخه‌ای مستقل از `master` با الگوی `phase/NN-name` آغاز می‌شود. وضعیت جاری در [دروازهٔ پذیرش](PHASE_PLAN.md#current-owner-gate) ثبت شده است.
3. توسعه و کامیت‌های فاز روی همان شاخه انجام شوند. اعتبارسنجی و بازبینی مالک طبق بستهٔ فاز تکمیل شوند؛ پایان کدنویسی به معنی پذیرش نیست.
4. پس از پذیرش صریح مالک و تکمیل closeout، به `master` برگردید و شاخهٔ فاز را با `git merge --no-ff <phase-branch>` ادغام کنید تا مرز فاز در تاریخچه بماند. تغییرات هم‌زمان `master` پیش از نهایی‌سازی باید در شاخهٔ فاز حل و اعتبارسنجی شوند.
5. روی کامیت نهایی `master` تگ annotated به شکل `stable/phase-NN` بسازید. برای اصلاح مستقل بعدی از نام تازه مانند `stable/phase-03.1` استفاده کنید؛ ابتدا تگ‌های محلی و ریموت بررسی شوند.
6. در محدودهٔ مجوز انتشار مالک، `master` و تگ مشخص به `origin` ارسال و هش‌ها و upstream بررسی شوند. تگ‌های نامرتبط ارسال نشوند.
7. پس از اطمینان از ادغام و انتشار تگ، شاخهٔ فاز در ریموت و با `git branch -d` در لوکال حذف شود. کار بعدی دوباره از `master` آغاز می‌شود؛ فاز بعدی خودکار شروع نمی‌شود.

برای اصلاحات خارج از فاز، شاخهٔ کوتاه‌عمر `chore/`، `fix/` یا `docs/` از `master` استفاده شود و پس از بازبینی و اعتبارسنجی به آن برگردد. این اصلاح نهایی ساختار با درخواست مستقیم مالک روی `master` انجام می‌شود.

## چرخهٔ هر بخش

1. پس از دستور صریح مالک برای شروع، دامنه و وضعیت «در دست توسعه» را طبق [برنامهٔ بخش‌ها](PHASE_PLAN.md#phase-sections) ثبت کنید و روی شاخهٔ فاز کار کنید.
2. پس از تأیید صریح توسعهٔ بخش، اعتبارسنجی صفحات و مسیرهای وابسته را ثبت کنید، وضعیت را به «تکمیل شد» تغییر دهید و کامیت تحویل بخش را روی شاخهٔ فاز بسازید. در صورت مجوز انتشار، همان شاخه را به ریموت ارسال کنید و هش کامیت منتشرشده را بررسی کنید.
3. ادغام با `master` و تگ نسخهٔ پایدار در چرخهٔ پذیرش نهایی فاز انجام می‌شوند. شروع بخش بعدی به دستور صریح مالک وابسته است.

## ثبت و اعتبارسنجی

- پیش از تعویض شاخه یا staging، `git status --short`، تغییرات عادی و stageشده و فایل‌های جدید بررسی شوند؛ تغییرات مالک حفظ شوند.
- فقط مسیرهای بازبینی‌شده با `git add -- <paths>` اضافه شوند. پیش از کامیت، `git diff --cached` و `git diff --cached --check` بررسی شوند.
- هر کامیت یک تغییر روشن با پیام‌هایی مانند `fix:`، `chore:` یا `docs:` باشد. اسرار، توکن‌ها، خروجی ساخت، وابستگی‌ها، کش و خروجی موقت تست ثبت نشوند.
- [کد بازبینی](../preview-review/) و [تأییدهای مالک](../preview-review/approvals.json) حفظ شوند. خروجی تولیدشده طبق [.gitignore](../.gitignore) ثبت نمی‌شود.
- اعتبارسنجی متناسب با تغییر از مسیر `npm run -s qa:affected` انجام شود. برای پذیرش کامل فاز، گزینهٔ `--full` را اجرا کنید. [دستورهای پروژه](../AGENTS.md) · [چک‌لیست QA](ai/QA_CHECKLIST.md)
- تغییر Git و تگ‌گذاری جای پذیرش محصول را نمی‌گیرد. برای این اصلاح مستندات و حذف solution خالی، بررسی diff، ساخت و lint انجام می‌شود؛ تست UI تازه‌ای ادعا نمی‌شود.

## ایمنی و بازیابی

- تاریخچهٔ منتشرشده rebase یا force-push نشود. از `reset --hard`، `clean -f`، حذف اجباری و کنارگذاشتن تغییرات استفاده نشود.
- پیش از حذف شاخه، حفظ تمام کامیت‌های آن در `master` یا تگ بررسی شود. حذف شاخه تاریخچهٔ مشترک را پاک نمی‌کند.
- برای مشاهدهٔ نسخهٔ قدیمی، تگ را در worktree یا شاخهٔ بررسی مجاز باز کنید؛ روی تگ استیبل توسعه ندهید.
- تغییر نام مخزن و انتشار این اصلاح طبق درخواست مستقیم مالک مجاز است؛ این مجوز شامل deploy، شروع فاز جدید یا توسعهٔ بک‌اند نیست.
