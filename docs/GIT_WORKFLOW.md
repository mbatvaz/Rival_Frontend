# گردش‌کار Git پروژهٔ RivalFrontend

## وضعیت مبنا

- شاخهٔ اصلی یکپارچه‌سازی کل پروژه `master` است؛ شاخهٔ بازیابی `chore/rival-recovery-1` با درخواست مالک حذف شد.
- کامیت بازیابی شمارهٔ ۱: `3ba35d67cf77ccaf1ae509fcc6287838c5a74a06` با پیام `chore: establish RivalFrontend recovery baseline 1`.
- این کامیت نقطهٔ بازیابی است؛ شمارهٔ آن به‌تنهایی نشانهٔ قبولی تست‌ها یا پذیرش فاز نیست.
- ریموت `origin` به `https://github.com/mbatvaz/Rival.git` متصل است.
- شاخهٔ `stable/baseline-1` در گیت‌هاب روی `f28ee4f7410d4806134abd551c11e9b46657865b` ثابت می‌ماند و شامل کامیت بازیابی و راهنمای اولیه است.
- تاریخچهٔ اولیهٔ گیت‌هاب با تاریخچهٔ محلی ادغام می‌شود؛ هیچ‌یک بازنویسی نمی‌شود. فایل solution اولیه خالی است و به معنی شروع بک‌اند یا فاز ۰۹ نیست.

## شاخه‌ها و ادغام

- `master` مسیر مشترک تمام بخش‌هاست؛ توسعهٔ روزانهٔ هر بخش روی شاخهٔ مخصوص آن انجام می‌شود.
- `frontend` شاخهٔ دائمی فرانت‌اند است و تمام تاریخچهٔ `stable/baseline-1` را دارد.
- `backend` شاخهٔ دائمی بک‌اند است؛ ساخت شاخه مجوز شروع پیاده‌سازی بک‌اند نیست.
- هر دو شاخه ابتدا از `master` یکپارچه منشعب می‌شوند. شاخه‌ها snapshot کل مخزن هستند؛ ساخت شاخه فایل‌ها را به پوشه‌های فرانت‌اند یا بک‌اند منتقل نمی‌کند.
- برای هر فاز فرانت‌اندِ صریحاً تخصیص‌یافته، شاخهٔ مستقلی از `frontend` بسازید؛ الگو: `phase/frontend-NN-name`، برای نمونه `phase/frontend-04-customer-panel`.
- فعلاً شاخهٔ فاز ۰۴ ساخته نمی‌شود؛ این فاز همچنان تخصیص‌نیافته است.
- نام `frontend/phase-04` با وجود شاخهٔ `frontend` قابل استفاده نیست؛ پیشوند `phase/` این تداخل نام را ندارد.
- برای کارهای خارج از فاز، پیشوندهای `feature/`، `fix/`، `refactor/` و `chore/` روی شاخهٔ بخش مربوط استفاده شوند.
- شاخهٔ اضافی صرفاً برای نمایش قرارداد نام‌گذاری ایجاد نکنید.
- پیش از تعویض شاخه، `git status --short` و تغییرات stageشده و عادی را بررسی کنید؛ تغییرات ثبت‌نشده ممکن است به شاخهٔ مقصد منتقل شوند.
- پس از توسعه، اعتبارسنجی و تأیید نهایی مالک، شاخهٔ فاز با `--no-ff` به `frontend` ادغام شود تا مرز فاز در تاریخچه بماند.
- روی همان کامیت نهایی `frontend`، شاخهٔ ثابت بعدی `stable/baseline-N` ساخته شود. شماره را با بررسی تمام شاخه‌های محلی و ریموت انتخاب کنید؛ شمارهٔ بعد از مبنای فعلی ۲ است.
- شاخهٔ baseline پس از ساخت تغییر نمی‌کند، مقصد توسعه نیست و برای آن کامیت خالی یا شمارهٔ ساختگی ایجاد نمی‌شود. baseline فرانت‌اند به معنی پذیرش بک‌اند یا نسخهٔ یکپارچه نیست.
- شاخهٔ فاز، `frontend` و baseline جدید در صورت مجوز ارسال به ریموت منتشر شوند؛ پیش از حذف محلی شاخهٔ فاز، حفظ تاریخچه و نسخهٔ ریموت بررسی شود.
- ادغام `frontend` یا `backend` به `master` فقط هنگام آمادگی نسخهٔ یکپارچه، پس از اعتبارسنجی و اجازهٔ مالک انجام شود. این راهنما مجوز دائمی ادغام نیست.
- پیش از ادامهٔ کار هر بخش، تغییرات تأییدشدهٔ `master` در شاخهٔ آن بخش ادغام شوند؛ تاریخچهٔ منتشرشده rebase نشود.
- حذف شاخه پس از اطمینان از حفظ کامیت‌ها، با `git branch -d` انجام شود؛ از حذف اجباری استفاده نکنید.

## ثبت تغییرات

- هر کامیت یک واحد قابل توضیح و بازبینی باشد؛ در پایان یک بخش منسجم کار ثبت شود.
- پیش از staging، `git diff` و فایل‌های جدید را بررسی کنید. از افزودن کورکورانهٔ همهٔ فایل‌ها خودداری کنید.
- فقط مسیرهای بررسی‌شده را با `git add -- <paths>` اضافه کنید.
- پیش از ثبت، `git diff --cached --stat`، `git diff --cached` و `git diff --cached --check` را بررسی کنید.
- اسرار، رمز واقعی، توکن، تنظیمات خصوصی و خروجی‌های موقت وارد کامیت نشوند. نمونه‌های تنظیمات نیز باید بازبینی شوند.
- پیام کوتاه و روشن باشد؛ پیشوندهایی مانند `fix:`، `chore:` و `docs:` نوع تغییر را مشخص می‌کنند.
- شمارهٔ نسخهٔ پایدار در نام شاخهٔ `stable/baseline-N` ثبت می‌شود؛ پیام کامیت باید تغییر واقعی را توضیح دهد. کامیت بازیابی اولیه استثنای ثبت‌شدهٔ تاریخی است.
- اصلاح کامیت‌های قبلی یا بازنویسی تاریخچه نیازمند اجازهٔ مشخص است.

## اعتبارسنجی و فایل‌های پروژه

- اعتبارسنجی متناسب با تغییر انجام شود؛ فرمان‌های پروژه شامل `npm run build`، `npm run lint`، `npm test` و `npm run test:subpath` هستند.
- برای تغییر رابط کاربری، الزامات [دستورهای پروژه](../AGENTS.md) و [چک‌لیست QA](ai/QA_CHECKLIST.md) رعایت شوند. ثبت Git جای پذیرش مالک را نمی‌گیرد.
- [کد بازبینی](../preview-review/) و [تأییدهای مالک](../preview-review/approvals.json) داده و کد پروژه‌اند و حفظ می‌شوند.
- فایل موقت نوشتن اتمیک تأییدها، خروجی ساخت، وابستگی‌ها، کش‌ها و تصاویر تولیدشدهٔ تست طبق [.gitignore](../.gitignore) ثبت نمی‌شوند.
- تفاوت پایان خط را پیش از اقدام با محتوای `HEAD` مقایسه کنید. اگر محتوای نرمال‌شده یکسان است، تازه‌سازی index فقط برای همان مسیرها مجاز است؛ بایت‌های فایل‌ها باید حفظ شوند. فایل‌ها را بازنویسی یا تنظیمات سراسری را عوض نکنید.
- کامیت بازیابی شمارهٔ ۱ یک خط خالی اضافی در انتهای [قالب دادهٔ بازبینی](../preview-review/format.js) را با اطلاع مالک حفظ کرده است.

## ریموت و ارسال

- سرویس میزبان و نشانی دقیق مخزن را مالک مشخص می‌کند؛ URL را حدس نزنید.
- مقصد فعلی `origin` مشخص و مورد تأیید مالک است. ساخت مخزن، تغییر مقصد و push تنها در محدودهٔ مجوز جاری انجام شوند.
- پیش از push، شاخهٔ محلی، مقصد و اختلاف تاریخچه بررسی شوند. از force push استفاده نکنید.
- برای شاخه‌های دائمی `master`، `frontend` و `backend`، upstream متناظر همان نام روی `origin` باشد؛ تطابق با مقایسهٔ هش و شمارش ahead/behind بررسی شود.
- هنگام کار، شاخهٔ بخش مربوط را فعال کنید؛ صرف ثبت کامیت به معنی ارسال آن به گیت‌هاب نیست.

## بازیابی امن و رفتار عامل

- ابتدا وضعیت، شاخه و تاریخچه را با فرمان‌های فقط‌خواندنی بررسی کنید؛ تغییرات مالک را حفظ کنید.
- برای بازگشت یک تغییر ثبت‌شده، پس از بازبینی و اجازهٔ لازم، کامیت معکوس با `git revert` بر بازنویسی تاریخچه ترجیح دارد.
- برای بررسی یک نقطهٔ قدیمی، در صورت نیاز یک شاخه یا worktree جدا و مجاز ایجاد کنید؛ کار ثبت‌نشده را کنار نگذارید.
- `git reset --hard`، `git clean -f`، بازنویسی فایل‌ها، حذف اجباری و بازنویسی تاریخچه بدون درخواست و توضیح خطر اجرا نشوند.
- مجوزهای جاری مالک ملاک‌اند؛ تأیید عمومی، اطلاعات نامعلوم مقصد ریموت یا اجازهٔ عملیات مخرب را تأمین نمی‌کند.
- دامنهٔ کار Git را به تغییر محصول یا شروع فاز بعدی گسترش ندهید. فاز ۰۴ همچنان تخصیص‌نیافته است.
